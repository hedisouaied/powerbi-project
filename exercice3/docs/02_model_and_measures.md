# Semantic model, relationships and measures

## Import (Power Query)

- Every CSV in `Mission_Control_Enterprise/` has one query in `powerquery/<table>.pq`, generated by `tools/build-pbip.ps1`.
- Each query does three things:
  1. Reads the file as UTF-8.
  2. Trims text with `fnCleanText`.
  3. Types each column from the profile of its values: text, date, date-time, whole number, decimal, currency `*_tnd`, percentage, boolean.
- Blank cells stay `null`. No row is dropped.
- The data folder is the model parameter `DataFolder` in `model.tmdl`. It points to `Mission_Control_Enterprise`.

### Validation

`tools/profile.ps1` checks the data against `DATA_DICTIONARY.md`:

| Check | Result |
|---|---|
| Primary keys | Unique in every table |
| Foreign keys | All valid. Only `calendar_events.related_project_id` (182) and `related_task_id` (215) are blank by design. |
| Order net vs. lines | Equals the sum of its lines for all 1,800 orders |
| Gross = net + tax | True for 1,799 of 1,800 orders. The planted exception is O00004. |
| Payments | One payment per order |
| Planted date anomaly | O00008: promised 2024-12-01, ordered 2025-04-18 |

## Star schema

**Shared dimensions:**
- `departments`, `employees`, `customers`, `products`, `suppliers`, `projects`.
- `dim_date`, marked as the date table.

**Fact and event tables:** every other table. They relate to the dimensions many-to-one, with a single filter direction.

**Relationships:** 61 in total, 12 of them inactive.

The inactive relationships remove every ambiguous path. They are kept for documentation and ad-hoc analysis (`USERELATIONSHIP`); no catalogue measure activates them today.

| Inactive relationship | Why |
|---|---|
| `employees.department_id → departments` | Facts relate to departments directly. A second path through employees would be ambiguous. |
| `payments.customer_id → customers` | Payments reach customers through `sales_orders`. |
| `payments.payment_date`, `payments.settlement_date → dim_date` | Payments are dated through their order. |
| `sales_orders.promised_delivery_date → dim_date` | Role-playing date |
| `projects.project_owner_id`, `projects.start_date`, `projects.planned_end_date` | Role-playing employee and dates |
| `tasks.department_id → departments` | Tasks reach departments through their project |
| `tasks.created_date → dim_date` | Role-playing date. `due_date` is the active one. |
| `missions.target_date → dim_date` | Role-playing date |
| `approval_requests.approver_employee_id → employees` | Role-playing employee. The requester is the active one. |

**No duplicated revenue.**
- Order amounts are only ever summed from `sales_orders`.
- Quantities and product cost come from `sales_order_items`.
- Nothing sums order amounts after joining to lines.

**What-if parameter:** `'Revenue Shock'` is `GENERATESERIES(-0.4, 0.4, 0.05)`.

## Business rules

| Rule | Definition |
|---|---|
| Revenue | Orders with status **Completed** or **Processing**. Cancelled and Returned are excluded. |
| Money received | Payments **Paid** and **Partial**. Outstanding = Pending + Overdue. Voided and Refunded are ignored. |
| Expenses | Every approval status except **Rejected** |
| Reference date | The last order date, **2026-11-22**. It is used instead of `TODAY()`, so "overdue" and "late" are reproducible. |
| Data-quality "open" | Issue status **Open** or **Under Review** |
| Salary | `employees.monthly_salary_tnd` is in the model but never sent to the visual |

## Visual feeds

Each table has a measure `Feed <table>` in the display folder `99 Visual Feeds`.

- It returns one JSON string, `{"c":[columns],"r":[[row values]]}`, built with `CONCATENATEX` and `FORMAT(…, "en-US")`.
- The 31 feeds total about 1.15 MB.
- `tools/csv-feeds.js` builds the same feeds from the CSVs. That is how the preview and tests run without Desktop. The CSV and model feeds were compared: 31 of 31 tables are identical.
